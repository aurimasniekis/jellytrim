# Testing

| Layer | Command | What it covers |
|---|---|---|
| Core | `dotnet test tests/Jellytrim.Core.Tests` | Policy semantics, path safety, accounting, ranking, migrations. Integration with **real SQLite and real files** in disposable sandboxes; only the media server is faked |
| Plugin | `dotnet test tests/Jellyfin.Plugin.Jellytrim.Tests` | Contract guards: authorization, no path input, no recursive delete, no Jellyfin file deletion |
| UI | `cd web && npm test` | Selection model, confirmation, escaping, states, accessible dialogs |
| End to end | `make e2e` | **A real Jellyfin 12.4 server**, real browser, generated media, real deletion, axe accessibility checks |
| Lifecycle | `python3 e2e/install_check.py` | Manifest install, upgrade, uninstall, reinstall on a real server |

Destructive tests only ever touch generated files. Core deletion goes through `SandboxDeleter`, which fails any path outside its temporary root. The e2e server only mounts `.e2e/run`, generated by `e2e/env.py` with ffmpeg. The server's internet metadata fetchers are turned off.

## Performance

Run with `JELLYTRIM_BENCH=1 dotnet test tests/Jellytrim.Core.Tests --filter "FullyQualifiedName~Hundred"`.

**Measured once on an Apple Silicon laptop, on 2026-11-01, Release build.** 102,000 items (18,000 movies, 2,000 shows of 40 episodes), 10 users, sparse state. Real scanner, SQLite and explorer. **Stat calls are stubbed and the media server is an in-memory fake**, so real-world scans add filesystem and Jellyfin query latency, and **this is not a measurement on real hardware or storage**.

| Operation | Target | Measured |
|---|---|---|
| First scan | under 60 s | 23.2 s |
| Rescan | under 60 s | 21.3 s |
| Evaluate one policy | under 3 s | 1.3 s |
| Explorer default page | under 200 ms | 18 ms |
| Explorer deep page, offset 70,000 | under 500 ms | 171 ms |
| Title search | under 500 ms | 35 ms |
| Watch filter, 3 users, movies | under 1 s | 340 ms |
| Watch filter, 3 users, shows | under 1 s | 522 ms |
| Eligibility filter | under 1 s | 280 ms |
| Watch summaries | under 1 s | 152 ms |
| Recommendations | under 3 s | 919 ms |
| Database size | | 119 MiB |

The first run of this benchmark found the eligibility filter at 19.5 s, which is fixed. Memory for evaluation was not isolated from the fake library, which is included in the 88 MiB heap figure.

The adapter's per-item inherited-tag lookup is not exercised here, because the server is faked. Not measured: a real 100,000-item Jellyfin server, network storage, memory peak during plan creation, or a plan at the 5,000-item limit.
